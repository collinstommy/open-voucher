Open Voucher · code audit · 4 Oct 2026

Refunds, deductions, and reports do not settle as one story.

A user's coin balance matches the sum of their transaction rows. That check can pass while the economy is still wrong. Claimer refunds, uploader clawbacks, replacements, and pool-status changes are separate switches. Several of them can fire twice, and several of them use the sticker price instead of what this voucher's ledger still owes.

The model the code is aiming at

Coins are created when someone uploads or signs up, and destroyed when someone claims. A €10 voucher pays the uploader 10 and charges the claimer 10, so a healthy claim changes who holds the coins and leaves the total supply alone.

Every balance change is supposed to go through applyCoinDelta in packages/backend/src/lib/coinLedger.ts. It floors the balance at 0 and writes a transaction for the change that actually happened. After that, sum(transactions.amount) for a user equals users.coins.

That invariant is about one account. It says nothing about whether a reported voucher was paid for twice, or whether the uploader still holds a reward for a voucher that was refunded to the claimer.

A voucher is settled when all three of these are true:

  1. The claimer has been made whole once: coins back, or one replacement voucher, not both.
  2. The uploader's reward has been taken back once, if the voucher was bad. Left in place, if it was good or simply expired unused.
  3. The voucher's pool status matches that decision, and the claimer id is cleared when it goes back on the shelf.

Today those three live in different rows, and most buttons only do one of them.

What already holds

  • Sound Signup, upload reward, claim spend, user return, failed photo delivery, and admin "Make Available" on a plain claimed voucher all go through applyCoinDelta. A plain claim cannot be refunded twice, because the first refund sets status back to available and clears claimerId.
  • Sound removeVoucherAndReverseCoins refuses a second run, and it reverses the net of the rows on that voucher. Expire-then-remove does not take the uploader's reward a second time, as long as the expiry deduction was recorded on that same voucher. The test in packages/backend/tests/convexTest/removeVoucher.test.ts covers that case.
  • Sound Upload reward and claim cost are the same number for each type. A paired "refund the claimer, claw back the uploader" is zero-sum.
  • Sound Clearing or admitting a report keeps the report row and drops it out of uploadReportCount / claimReportCount via recalculateReportCounts.
  • Sound The manual deduct form on the user page refuses an amount above the current balance.

Issues, with worked examples

P0 · money can be created · bot callbacks

1. A report can pay the claimer twice

refundReportedVoucher and requestReplacement in packages/backend/convex/vouchers.ts do not look at each other. Neither checks that this user claimed the voucher, that a report exists, or that this voucher was already compensated. Both write type: "refund" for the full claim cost. The replacement writes replacement_received with amount 0 on the other voucher.

The Telegram buttons are the only guard. report_replacement_yes and report_replacement_no edit the message and then run the mutation. Those are not one atomic step. Two taps, or a second webhook delivery while the first send is still in flight, both get through. packages/backend/convex/http.ts waits for the whole callback before it returns 200, which is exactly when Telegram retries.

There is a type report_refund in the schema and in both UIs. Nothing writes it. Report refunds and "the photo failed to send" refunds share the bucket refund.

€10. Claimer paid 10, then both buttons run.
StepClaimer coinsWhat they hold
After claim−10Voucher A
"No thanks" refund0Nothing
"Yes" replacement, same report0Voucher B, unpaid

Supply is then the two upload rewards, and the claimer's payment has been printed back. A clean claim of B would have left supply unchanged. This path leaves supply 20 coins high, and the claimer holds a voucher they no longer paid for.

The same functions mint coins even with no prior spend. The tests expect that: refundReportedVoucher takes a claimer from 10 to 20 with no claim_spend row. That is the function working as written.

If no replacement is in stock, requestReplacement refunds and returns. Calling it again refunds again. The handler also tells the user their coins were refunded for every non-replacement result, including not_found.

Fix

Put one settlement on the report: none, refunded, or replaced. Both mutations return the existing settlement if it is already set. Write report_refund on the original voucher, and point replacementVoucherId at the new one. Do this in the mutation, not in the button handler.

P0 · claimer keeps a dead voucher and the coins stay spent

2. Replacements skip the expiry rule and prefer the oldest voucher

requestVoucher only offers vouchers with expiryDate > now, then picks the one that expires soonest. requestReplacement queries available plus validFrom, then calls .first(). No expiry check. Index order on by_status_type is oldest first.

The nightly cron (expireOldVouchers, 01:01 UTC) is what flips past-expiry vouchers off available. Until it runs, and whenever it misses, those rows are still available. A replacement is likely to be one of them.

My Claims only lists status === "claimed" and expiryDate > now. An expired replacement is claimed, hidden, and cannot be returned from the app. The claimer already paid on the original. They do not get a refund, because a replacement was "found".

Fix

Use the same availability filter as a claim: not expired, already valid, soonest expiry first. If none qualify, refund once and record that settlement.

P0 · admin remove · replacements

3. "Remove & reverse" refunds a claim that was already settled by a replacement

removeVoucherAndReverseCoins sums transactions where voucherId is this voucher, then applies the opposite. A replacement records a 0-coin row on the new voucher, not on the original. The original still shows claim_spend −10. Remove sees −10 and gives the claimer 10 back. They keep voucher B.

Uploader AUploader BClaimerHolds
A and B uploaded, A claimed+10+10−10A
Replacement B issued+10+10−10B
Fair settlement0+10−10B
What Remove does to A0+100B

The confirm dialog makes this worse. If claimerId is set, it always says both people get a reversing entry. On a replacement voucher the claimer's net is 0, so they get nothing, lose B, and the original −10 stays. Removing the replacement strands them. Removing the original pays them and lets them keep B.

Manual report deductions never get a voucherId (deductUserCoins), so Remove cannot see them and will not undo them. A "Reports" deduction plus Remove is two punishments.

Fix

Treat Remove as a tombstone so the barcode cannot be uploaded again. Reverse coins only for value that is still unsettled on this voucher. If the claimer already holds replacementVoucherId, their original spend stays spent. Say the actual coin deltas in the confirm dialog, including "no coin change".

P0 · sticker price, not the ledger · user return and Make Available

4. Returning a replacement pays the claim cost, even when the spend lives on a different voucher

returnClaimedVoucher and reverseClaim add CLAIM_COSTS[type]. They do not read the ledger. For a normal claim that matches the one claim_spend row, and the status guard stops a second refund. That path is fine.

A replacement is claimed, shows in My Claims, and shows a coin value of 10. "Return to pool" adds 10. That is fair when the original spend is still outstanding: −10 on A, +10 on B, net zero, B back in the pool.

It is a mint when the original was also refunded (issue 1), or when an admin then presses Make Available on B as well. Make Available is the same flat credit, under the name claim_reversed.

Fix

Refund the unsettled net for this claim, once. A replacement's unsettled net is 0 unless you deliberately want "return B" to unwind the original spend. If you do, unwind that original row, and mark both vouchers settled so a later refund cannot fire.

P1 · the structural hole · every bad voucher

5. The uploader keeps the reward unless they confess

The claimer is offered a refund or a replacement immediately, before the uploader answers. confirmUploaderUsedVoucher is the only automatic clawback. It subtracts UPLOAD_REWARDS[type] and sets the report outcome to uploader_admitted, which drops the report out of the counts.

recordUploaderDenied writes a 0-coin uploader_denied row, sets that outcome, and leaves the reward in place. Silence does the same: the report stays open and the reward stays. Admin "Expire & Clear" and "Available & Clear" also leave both balances alone.

Claimer already refunded. Uploader does not admit.
UploaderClaimerVoucherSupply vs a clean unused upload
Uploaded, claimed, refunded, denied or ignored+100Dead+10
Same, but they got a replacement from B+10−10A dead, holds B+10

Each bad voucher that is not confessed mints its reward for good. A chain of reported replacements mints one reward per link. The claimer is whole. The supply is not.

Admit itself is not guarded. The mutation does not check status. A second delivery, or a double tap before the button disappears, subtracts the reward again. Deny and admit can also race: the last write wins the status, and the deduction still happens.

Fix

Decide the policy in one place. If the claimer was made whole, claw the upload reward once, unless an admin explicitly says the report was false. Record uploaderClawback on the voucher or report and refuse a second one. Denial can dispute that, but it should be a recorded decision, not a silent keep.

P1 · stacks on top of other penalties · admin upload card

6. "Expire & Deduct" takes the sticker reward again, on almost any status

expireVoucherAndDeductCoins rejects only expired. The button is hidden for removed and expired, and shown for everything else: available, claimed, reported, invalidated, uploader_admitted_used, uploader_denied. It always subtracts the full upload reward. It does not read self_invalidated, uploader_refund, or an earlier admin deduction. It does not refund the claimer, clear claimerId, or close the report.

There is no confirm dialog. One click.

Worked case. Uploader admits (−10, balance back to where it was before the upload). They still have other coins. Admin then presses Expire & Deduct. Another −10 leaves the account. The report row stays open if they had not admitted, or stays admitted while the voucher is now expired. The user page still shows the report, and the stat counter may already have dropped it.

The other face of the same button: the cron expires unused vouchers and lets the uploader keep the reward. Once status is expired, Expire & Deduct throws and the button disappears. The penalty path vanishes for the vouchers the cron already retired. Remove is still there, and Remove will claw that reward, because the ledger net is still +10.

The mutation returns deductedAmount as the full reward even when the balance floor reduced it. The screen ignores the return value today. A caller that displayed it would overstate the deduction.

Fix

Split the button. "Mark expired" only changes status. "Claw back upload reward" runs once, for the unsettled reward, and shows the real amount. Hide it when a clawback row already exists. Confirm before either write. Leave the cron's "keep the reward on natural expiry" as its own rule, and say so on vouchers the cron already expired.

P1 · pool status and coins disagree · report cards

7. "Available & Clear" puts the voucher back on the shelf without settling either person

clearReportAndUpdateVoucher sets the voucher to expired or available, sets the report outcome to admin_cleared, and recounts. It does not change coins. It does not clear claimerId or claimedAt. It can be run again and flip the status back.

"Expire & Clear" and "Expire & Deduct" share the word expire. One takes coins. The other does not.

After Available & Clear the voucher matches requestVoucher's query (status === "available", expiry still in the future). The next person can be charged for it. The original claimer id is still on the row until that claim overwrites it, so it still counts toward the original claimer's 5-a-day limit. Their Telegram photo of the barcode is still on their phone. If they were already refunded, they have the coins and the barcode, and someone else is about to pay for the same barcode.

The report then drops out of the counts. The header stat goes down. The tab still lists the card, with no outcome on it, because getUserDetails does not return outcome, resolvedAt, or replacementVoucherId.

Fix

Split into "Dismiss report" (outcome only) and "Put back in the pool". The pool action clears claimerId and claimedAt, and it should refuse while the claimer is unpaid and still the holder, or while they were refunded and the barcode may still be live. Show the outcome on the card so a cleared report is obvious.

P1 · admin claimed tab

8. "Make Available" is a refund button shown on rows it cannot refund

The Claimed tab lists every voucher with this user as claimerId, whatever the status. Reported, expired, removed, admitted, denied, and a voucher put back in the pool by Available & Clear all appear. Every card gets Make Available.

reverseClaim requires status === "claimed". On a reported voucher the mutation throws. The page never reads isError for this mutation, or for expire, remove, or clear. The click ends and the card looks unchanged.

When it does work, there is no confirm, and the label does not say that coins move. On a plain claim the amount is right. On a replacement it is the mint in issue 4.

Fix

Show the button only for claimed. Label it "Return to pool and refund N coins", with N taken from the unsettled spend. Confirm. Show the error if the mutation throws. Other statuses need their own actions, or no action.

P1 · the floor hides unpaid penalties

9. A short balance turns a full penalty into a smaller one, and then forgets the rest

applyCoinDelta floors at 0 and stores the smaller delta. The user's balance still matches their ledger. The voucher can still be fully killed.

The floor on "I used this" is intentional (docs/superpowers/specs/2026-05-25-self-invalidate-voucher-design.md). The hole is what happens around it. The confirm says the full coin value will be deducted. If they uploaded a €5 (15 coins), spent those coins on other claims, and then mark the upload used, the ledger writes 0, the voucher leaves the pool, and nothing records the 15 that was not collected. Expire & Deduct on that same voucher will try to take 15 again later, from whatever they have earned since.

Admin Expire & Deduct uses the same floor and does not warn. The manual deduct form is the only place that blocks an amount above the balance.

Fix

Either refuse the action unless the full amount can be taken, or store the uncollected remainder on the voucher and block further claims until it is paid. Stop issuing a second full penalty on top of a partial one. Tell the user the amount that will actually move.

P1 · admin analytics and the user transaction list

10. The reports of these actions are mislabeled, and they count rows rather than coins

getTransactionTotalsByType counts transactions. The analytics stat says that number is "coins moved between users". Coins are not moved between users. Upload and signup create them. Claims and penalties destroy them. Refunds create them again. A lot of the rows are amount 0 (replacement_received, uploader_denied, and clamped deductions that moved nothing).

The labels in apps/web/src/routes/admin/analytics.tsx are swapped:

Stored typeWho writes itLabel on the analytics page
claim_returnedUser, "Return to pool"Admin claim returned
claim_reversedAdmin, "Make Available"User returned

uploader_refund is a deduction (the uploader admitted they used it). The analytics label is "Uploader refund", and the user app falls through to the same words. It reads like money given back. The amount is negative, which is the only clue.

report_refund is labeled in both UIs and never written.

The user app shows the last 25 rows (getTransactionHistory). A balance cannot be rebuilt from that list. The admin user page does load the full ledger, then mixes it with report rows that have no outcome and no link to the voucher's settlement. A refund, a 0-coin replacement, and a report on the same voucher look like three unrelated events.

The stat chips use uploadReportCount and claimReportCount, which skip admin_cleared and uploader_admitted. The tab badges count every report row. The two numbers disagree, and the cards do not say why.

Fix

Show count and sum of amount separately. Drop 0-coin markers from the money chart, or put them in an events chart. Swap the two claim labels back. Rename uploader_refund in the UI to something like "Upload reward taken back". On the user page, group by voucher: report outcome, claimer settlement, uploader clawback, net coins.

P2 · stats drift if the backfill is run

11. Recounting users from scratch undoes Remove

backfillUserStats increments uploadCount for every voucher row, including removed, and increments claimCount whenever claimerId is set. Remove decrements those counters and leaves claimerId in place. A later backfill puts the removed voucher back into both counts. Refunded reports also keep claimerId, so they stay in the claim count, which may be what you want for "they did claim it" and is not what Remove just recorded.

Fix

Define the counters once. If Remove means "this upload no longer counts", the backfill has to skip removed. If a refunded claim still counts, say that, and stop decrementing it in one path and not the other (refundFailedClaimDelivery and user return decrement; a report refund does not).

P2 · deduction form

12. "Reports" deduct is a label, not a settlement

The two chips, Reports and Manual, only pick admin_report_deduction or admin_manual_deduction. The amount is free text. The row has no voucher id, does not close any report, and does not reduce uploadReportCount. An admin can deduct "for reports", then Expire & Deduct the same uploads, then Remove them. Each step still looks available.

Fix

Keep a free-text manual adjustment, with a note. Build the report penalty as "claw back these vouchers", which uses the once-only clawback from issue 5 and marks those reports.

A shape for the fix

One settlement per reported claim, written inside the mutation that moves the money.

  • claimerSettlement: none, refunded, or replaced (with the replacement id). A second call returns the first result.
  • uploaderClawback: none or the amount actually taken, plus any uncollected remainder. A second clawback does nothing.
  • Pool status is a separate write. It clears claimerId when the voucher goes back out. It does not move coins.

Buttons worth splitting:

  • Expire & Deduct → "Mark expired" and "Take back the upload reward".
  • Remove & reverse → "Remove from the pool" (tombstone) and, only if something is still unsettled, "Undo the remaining coins", with the real numbers in the confirm.
  • Expire & Clear / Available & Clear → "Dismiss report" and "Put back in the pool".
  • Make Available → one button, only on a live claim, named for the refund it performs.
  • Reports deduct → a chooser of vouchers to claw back, not a free amount with a report-flavoured type.

Replacement selection should call the same helper as a normal claim. Analytics should sum amount and use the labels that match the writers. The user page should show, per voucher, the report outcome and the two settlement fields, so the transaction list is a detail view rather than the only view.

Tests to add before changing the writers: second refund is a no-op; refund then replacement is a no-op; replacement cannot be an expired voucher; Remove after a replacement does not pay the claimer; Expire & Deduct after admit does not charge again; Available & Clear does not leave claimerId set; analytics labels match claim_returned and claim_reversed.

What this audit did not do

This is from the current code and its tests. I did not reconcile production balances, so I cannot say how many live vouchers already have two compensation rows or an unclawed reward. A read-only pass can count those without changing data: users whose transaction sum differs from coins, vouchers with more than one positive refund-like row for the same user, and originals that have both a refund and a replacement.

I also left timezone edges alone (report rate-limit midnight versus Irish dates, the 9pm return rule). They are real, and they are not what unbalances the books.
