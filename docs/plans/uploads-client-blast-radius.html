Open voucher · design note · not implemented

Stop threading client through OCR. Track the attempt instead.

Android needs upload, spinner, then success or fail. That is a row in uploads. Telegram still needs a Bot API message. That is a Telegram-only wrapper around the same write. Neither job belongs inside storeVoucherFromOcr.

One photo, two doors

Same linked account. Telegram chat id and a Google identity. The person uploads a voucher photo. The domain write is identical: accept or reject the image, maybe create a voucher, maybe credit coins. Delivery is not.

Telegram

Webhook already said “Processing…”. When OCR finishes, send a Bot API message. The HTTP request that started this is gone, so the send has to live in the scheduled action the bot queued.

Android

submitUpload returns immediately with { accepted: true, uploadId }. The app useQuerys that one document. Spinner while processing. Then the same document becomes succeeded or failed.

Daily limit never creates an upload row. It is a synchronous return from the mutation. Telegram’s webhook sends the limit copy. Android shows it from the mutation result.

What the code does now

client is minted at login, stuffed onto the JWT, injected by userMutation, passed into uploadVoucherForUser, scheduled into processVoucherImage, and checked again inside storeVoucherFromOcr and notifyUser. OCR is domain code wearing a Telegram adapter.

The scheduled function id from runAfter cannot drive the spinner. Validation failure still completes the action as success. You need an application row that exists before OCR starts.

Proposed flow

Schedule from the mutation, not from the Telegram action after the mutation returns. Convex only guarantees the scheduled function if the mutation commits. That is why there are two thin mutations instead of one helper that returns and lets the HTTP caller schedule.

Who writes uploads

WhenWriterRow
Mutation accepts the image acceptUpload in vouchers.ts { status: "processing", userId, imageStorageId }. Returns uploadId.
OCR validates and stores a voucher storeVoucherFromOcr Patch succeeded + voucherId.
OCR validation reject storeVoucherFromOcr Patch failed + failureReason. Still insert failedUploads for admin.
Gemini / extract throws recordSystemError Patch failed + SYSTEM_ERROR. Insert failedUploads as today.
Daily limit Nobody No row. { accepted: false, reason: "daily_limit" }.

Pass uploadId through the scheduler, not client. The attempt is the correlation id.

Table shape

A union, not a bag of optionals. Convex stores one table. The TypeScript result type is the contract the app matches on. 

{
	uploads: defineTable({
		userId: v.id("users"),
		imageStorageId: v.id("_storage"),
		status: v.union(
			v.literal("processing"),
			v.literal("succeeded"),
			v.literal("failed"),
		),
		voucherId: v.optional(v.id("vouchers")),
		failureReason: v.optional(v.string()),
	}).index("by_userId", ["userId"]),
}

Public query getUpload({ uploadId }) is a userQuery: owner only, returns the row plus a user-facing message derived with uploadFailureBody. Do not list failedUploads on the upload screen.

Android subscribe

const result = await mutation(api.vouchers.submitUpload, { imageStorageId });
if (!result.accepted) {
	show("Daily limit"); // no query
	return;
}
const upload = useQuery(api.vouchers.getUpload, { uploadId: result.uploadId });
if (upload === undefined) return <Spinner />; // convex loading
if (upload.status === "processing") return <Spinner />;
if (upload.status === "succeeded") return <Accepted voucherId={upload.voucherId} />;
return <Failed reason={upload.failureReason} message={upload.message} />;

That is the whole app UX. No list of historical failures on this screen. getMyAvailableUploads stays the library of kept vouchers.
